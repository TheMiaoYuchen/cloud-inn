# Cloud Inn 产品与技术设计

日期：2026-07-25

状态：已完成讨论，待用户审阅书面规格

首发平台：macOS 桌面应用

## 1. 产品愿景

Cloud Inn 是一款以生成式 AI 辅助空间创作为核心的高奢酒店模拟经营游戏。玩家在像素化网格中规划真实尺度的客房与公共空间，通过文字和预设定义设计风格，由 AI 生成连贯的空间效果图；随后将房型布置到多楼层酒店中，并通过定价、服务、客群匹配和扩建形成长期经营循环。

游戏的首要目标是让玩家轻松实现对高奢酒店的想象，而不是复刻专业建筑软件或高压经营模拟。整体气质参考文华东方与四季酒店所代表的克制、精致和地域文化表达，但 Cloud Inn 建立自己的设计语言，不直接复制具体酒店或客房。

## 2. 核心原则

1. **创作、规划、经营形成完整闭环。** 首版不把单一模块做成孤立工具。
2. **轻松但有因果。** 设计、面积、设施和服务会影响成本、客群、价格与评价，但不要求繁琐微观管理。
3. **AI 增强表现，不控制胜负。** 所有经营数值由本地确定性规则计算；AI 负责效果图和少量可选叙事。
4. **一致性优先于单张图片的惊艳度。** 同一房间的多张图必须像一个完整空间，同一设计系列必须共享可辨认的设计基因。
5. **本地优先。** 不要求账号；离线可经营；存档、图片和 API 密钥由本机安全管理。
6. **先经营一家酒店，预留长期扩展。** 首版不做集团玩法，但数据边界允许未来加入城市、分店、度假村和品牌标准复用。

## 3. 目标体验与成功标准

### 3.1 目标玩家

首个版本以开发者本人在 Mac 上长期游玩为主。内容成熟后再考虑公开发布和 Windows 版本。

### 3.2 核心循环

1. 规划酒店品牌风格和建设方向。
2. 绘制房间或公共空间的户型与功能区。
3. 放置关键家具和高奢设施，设定风格与材质。
4. 查看造价和经营潜力，提交 AI 设计委托。
5. 评审主视觉与重点区域图，采纳为房型或设计系列。
6. 将房型放入楼层，规划走廊、核心设施与后勤动线。
7. 施工、开业并经营酒店。
8. 从入住率、客群反馈、口碑和现金流中发现问题。
9. 调价、改善服务、翻修、增加房型或扩建楼层，再次进入循环。

### 3.3 首版成功标准

- 玩家可从毛坯楼层开始，独立完成第一种房型、大堂、楼层规划和开业。
- 设计选择能明确反映到造价、房型定位、客群偏好、入住率和收益潜力。
- 同一房间的主视觉与区域图在色板、材质、家具语言和灯光上保持明显一致。
- 100 间以上客房与多楼层同时经营时，界面和模拟保持流畅。
- AI 服务断开或生成失败时，现有酒店仍可完整经营。
- 存档可在异常退出后恢复，并能完整导出后重新导入。

## 4. 产品形态

采用轻量桌面应用，而非纯 Swift 原生或纯网页：

- **Tauri** 提供 macOS 应用外壳、窗口、本地文件、钥匙串和打包能力。
- **React + TypeScript** 实现经营界面、设计向导、报表和状态管理。
- **PixiJS** 实现房间网格、楼层画布、拖拽缩放和像素人物动线。
- **SQLite** 保存结构化存档；图片以本地资产文件保存。

该方案接近网页开发速度和 Token 成本，同时获得可靠本地存档、安全密钥管理和桌面游戏体验。未来 Windows 版可复用绝大多数代码。

## 5. 游戏时间与难度

### 5.1 时间系统

- 设计和施工规划时可暂停。
- 营业时自动推进，支持正常、2 倍和 4 倍速度。
- 正常速度下，一个游戏日约 10 至 15 分钟。
- 每日生成简洁结算，每 7 日生成周报，每 30 日进行月度结算。
- 日结、周报和月度数字均由本地规则生成，不调用 AI。
- 玩家可选择让 AI 根据已计算数据撰写月度顾问点评。
- 离线最多结算 7 个游戏日；离线期间不触发会造成重大损失的事件。

### 5.2 难度

- **休闲模式（默认）：** 不会破产。现金紧张会暂停施工、降低服务能力并带来贷款压力，但存档不会强制结束。
- **经营模式：** 长期亏损可能进入债务重组，经营约束更强。
- 两种模式均允许手动存档和恢复历史版本。

## 6. 开局与成长

### 6.1 开局

玩家从空白酒店筹建开始，接手摩天楼中的若干毛坯楼层，依次确定：

1. 酒店品牌设计基因。
2. 空中大堂位置与基本功能。
3. 第一套客房设计。
4. 第一个标准客房层。
5. 基础服务部门与开业价格。

教程提供一套可直接采用的基础方案，帮助玩家快速开业，但不会未经确认自动施工。

### 6.2 成长

- 施工、翻修和购买楼层消耗资金。
- 优质楼层、稀有设施、高级合作和高价值客群需要酒店声望。
- 声望来自设计品质、宾客口碑、服务表现和稳定经营。
- 声望是软门槛：不强制固定任务顺序，已解锁内容不会因声望下降而收回。
- 设计阶段不限制想象；施工阶段才检查资金。
- 资金不足时可保存蓝图、分期施工或使用适度贷款。

## 7. 品牌与设计风格系统

### 7.1 三层设计基因

1. **酒店品牌基因：** 全酒店默认共享的主色、核心材质、家具轮廓、东方元素表达、灯光气质和禁用元素。
2. **设计系列基因：** 在品牌基因上形成可复用的变体，如禅意庭院系列、都市暖木系列或海派艺术系列。
3. **单间空间变化：** 记录某间客房或某个功能区的局部变化。

这是软统一系统：同一房间内部必须高度一致；不同客房可以采用差异明显的系列；少量特色房可明显偏离品牌。系统显示协调度并解释偏离原因，但不阻止玩家创作。

### 7.2 风格预设

首批预设从文华东方与四季酒店的公开案例中提炼通用设计语言，例如：

- 当代东方静奢
- 都市暖木行政
- 岭南花园雅致
- 海岛自然奢华
- 克制山水现代
- 艺术收藏宅邸

预设由可组合字段构成，包括色板、材质、灯光、家具语言、纹样密度、地域文化表达和禁用元素。选择预设后，系统将其具体字段注入生成提示词，不把酒店品牌名称本身作为提示词捷径。

## 8. 房间设计器

### 8.1 户型网格

- 网格边长为 0.5 米，每格代表 0.25 平方米。
- 玩家先拖拽矩形快速建立功能区，再用像素画笔逐格增减和修整。
- 门、窗、出入口和通道使用专门工具放置。
- 系统实时显示总面积、各功能区面积、未划分区域和不可达区域。
- 系统提供动线与空间建议，但不会擅自修改户型。

### 8.2 功能区

客房可包含玄关、卧室、起居室、办公区、卫浴、独立卫生间、衣帽间、茶饮区、厨房或备餐区、露台等。不同房型可定义自己的必需区和可选区。

### 8.3 关键物件库

首版目标约 40 至 60 种关键物件，按高奢酒店体验分类：

- 睡眠：特大床、双床、床尾凳、婴儿床、加床。
- 起居办公：沙发、扶手椅、书桌、餐桌、茶席、壁炉。
- 卫浴更衣：独立浴缸、淋浴、双台盆、梳妆台、步入式衣帽间。
- 餐饮茶饮：迷你吧、咖啡台、酒柜、小厨房。
- 玄关收纳：行李台、衣柜、全身镜、换鞋凳。
- 景观特色：落地窗、露台座椅、户外浴缸、小型泳池。
- 艺术与体验：艺术陈列、屏风、阅读角和地域文化特色设施。

物件具有标准尺寸，可旋转、贴墙、对齐和复制。物件既指导 AI 构图，也轻度影响舒适、卫浴、办公、私密、景观等体验评分，并计入建造成本。装饰细节仍主要通过描述控制，避免变成专业室内设计软件。

### 8.4 五步设计流程

1. 绘制户型和功能区。
2. 放置关键家具与设施。
3. 为整体和各功能区设置风格、材质、色彩、灯光、特色和自由描述。
4. 查看造价、体验评分、房型建议与收益潜力。
5. 提交 AI 设计委托，评审后保存为房型或设计系列。

右侧属性面板只显示当前选中空间或物件的相关字段，避免一次展示大量参数。不想细调时，玩家可让系统按品牌基因补全未指定内容。

### 8.5 造价与经营结果

每个设计产生三类结果：

- **建造成本：** 面积、墙体、门窗、材质档次、家具与特色设施共同决定。
- **运营表现：** 舒适、卫浴、办公、景观、隔音、私密性、动线和服务便利等评分。
- **收益潜力：** 房型等级、适合客群、建议售价区间和预计入住表现。

同一房型蓝图可重复使用，但每次在楼层放置都会产生实际建造成本。翻修与升级单独计价。

## 9. AI 设计事务所

### 9.1 生成颗粒度

- 每个房间或公共空间先生成一张整屋主视觉。
- 玩家选择 1 至 3 个重点区域生成附加效果图。
- 可随时为其他区域补图，不必重做整个空间。
- 公共空间采用相同规则，例如大堂的入口、接待和休息区，餐厅的主餐区、包间和吧台。

### 9.2 一致性机制

一致性由多重信息共同保证：

1. 固定的酒店、系列和房间设计基因。
2. 户型关系、关键物件与空间描述。
3. 已采纳的整屋主视觉作为后续区域图的参考图。
4. 固定色板、材质、家具语言、灯光和禁用元素。
5. 局部重绘时明确锁定未选区域和未要求改变的元素。
6. 保存请求参数、参考图、输出和版本关系，允许比较与回退。

应用显示色板、材质、家具语言和灯光的一致性检查结果，但最终采纳权属于玩家。

### 9.3 任务队列

- 生成任务以游戏内“设计委托”形式进入后台队列。
- 玩家等待时可以继续设计或经营。
- 完成后通知玩家进入方案评审。
- 失败任务可重试、取消或切换备用模型，不影响蓝图、存档和营业。
- 设置中显示预计调用次数，支持每日额度和生成前确认。

### 9.4 模型与 API 适配

初步选定 API Nebula `nanobanana` 令牌分组：

- 主模型：`gemini-3.1-flash-image`
- 备用模型：`gemini-2.5-flash-image`
- 模型列表在运行时通过 `GET /v1/models` 校验，避免上游调整后继续调用已下线模型。
- 请求接口：`POST https://img-api.apinebula.ai/v1beta/models/{model}:generateContent`
- 鉴权：`Authorization: Bearer <API_KEY>`
- 文本生图通过 `contents[].parts[].text` 传入提示词。
- 参考图编辑在同一条用户消息的 `parts` 中同时传入文字和 `inlineData` 图片。
- 仅需图片时使用 `generationConfig.responseModalities: ["IMAGE"]`。
- 通过 `generationConfig.imageConfig` 设置比例和分辨率。
- `gemini-3.1-flash-image` 支持 1K、2K、4K；`gemini-2.5-flash-image` 仅支持 1K。
- 默认评审图使用 1K 以控制时间和费用；玩家采纳后可选择用主模型生成 2K 或 4K 成品。
- 返回图片位于 `candidates[0].content.parts[].inlineData`，应用按实际 `mimeType` 解码并立即写入资产文件。
- 完整 Base64 响应不写入数据库或日志。
- 2K/4K 请求采用更长超时，并限制并发，避免大响应造成内存峰值。

模型调用封装在独立适配层中。游戏核心只提交标准化的生成任务，不直接依赖 API Nebula 的具体请求结构。未来更换供应商或模型不应改变房间、楼层或经营数据。

API 依据：[API Nebula nanobanana 分组文档](https://docs.apinebula.ai/docs/advanced/image/nanobanana)，核对日期 2026-07-25。

### 9.5 文本 AI 边界

- 普通住客、预订、评价分数、财务和报表不调用 AI。
- 规则模板生成日结、周报、流失原因和常规评论。
- AI 可选地用于重要住客、特色评论、重大事件和月度顾问点评。
- 关闭文本 AI 后，所有经营功能仍然完整。

## 10. 建筑与楼层管理

### 10.1 建筑模板

系统支持独栋酒店与摩天楼酒店两类建筑模板。首个场景优先制作“摩天楼中的酒店”：

- 酒店占据若干连续或分段楼层。
- 拥有专属地面入口与空中大堂。
- 非酒店楼层由写字楼、商业或公寓占用，只作为背景。
- 玩家可逐步购买或改造更多楼层、侧翼和户外区域。
- 首版不允许自由绘制建筑外形。

### 10.2 垂直总览

默认主界面显示整栋摩天楼和酒店楼层。玩家可看到大堂、客房层、餐饮、水疗和设备层的垂直关系，点击楼层进入平面视图。标准客房层可保存为楼层模板、复制到其他楼层并比较差异。

### 10.3 平面视图

- 中央平面图占界面主要面积。
- 左侧垂直楼层栏和右侧检查栏均可折叠。
- 房间按其真实户型面积和轮廓显示，不能被统一大小的卡片替代。
- AI 主视觉可作为房间缩略底图，但只铺在真实边界内。
- 远景显示缩略图、房号和房态；中景显示功能区和入口；近景显示 0.5 米网格、门窗、设施和编辑节点。
- 可关闭缩略图，切换到纯户型、房态房价或经营效率视图。

### 10.4 房型放置与变体

- 房型从房型库拖入，可旋转、镜像和有限拉伸。
- 小幅调整会同步检查家具、面积、造价和效果图适配。
- 大幅改变面积或功能区会建立新的房型变体，并提示重新确认造价和效果图。
- 房间面积在户型编辑器和楼层总览中保持同一比例。

### 10.5 走廊与核心筒

玩家绘制主要走廊，并放置电梯、楼梯、布草间、员工通道和后勤设施。系统提供连通、服务距离、拥堵和疏散建议，但不自动改图。

近方形塔楼的主要客房层采用可编辑的“中央核心筒 + 环形走廊 + 外圈客房”结构：

- 核心筒包含客梯、员工梯、消防楼梯、管井、设备和部分后勤。
- 环形走廊围绕核心筒形成回路。
- 客房沿外立面布置，转角优先用于较大的景观套房。
- 42 平方米标准房、55 平方米行政房和 85 至 118 平方米套房会占据不同外墙长度和楼层面积。
- 狭长楼层可使用双走廊，异形楼层可使用局部环路和分支；环形不是强制模板。

### 10.6 营业动线

楼层中显示少量像素住客、员工、行李和清扫车，表达入住、送餐、清扫和拥堵。人物是群体模拟的视觉反馈，不为每位普通住客运行完整日程或 AI，因此多楼层和百间客房仍保持轻量。

## 11. 客群与预订

### 11.1 首批客群

- 商务
- 情侣
- 家庭
- 度假
- 高净值
- 文化体验

### 11.2 需求模型

每类客群具有硬条件和偏好权重。

硬条件包括单床或双床、可住人数、最低面积、连通房等。不满足硬条件时，预订概率接近零。

偏好包括办公区、浴缸、双台盆、衣帽空间、隔音、景观、儿童友好、餐饮便利、私密性、设计风格和价格敏感度。偏好不匹配会降低预订概率或评价。

房间更大、更贵不代表适合所有客群。系统先匹配需求，再评估价格和口碑。

### 11.3 信息发现

- 开业前显示直观的客群画像，不展示全部计算权重。
- 营业后通过订单流失原因、宾客评价和市场报告逐步揭示具体需求。
- 后期可解锁市场研究，明确显示需求趋势。
- 反馈必须解释原因，避免经营结果成为黑箱。

## 12. 价格、房态与财务

### 12.1 房价

- 玩家为每种房型设置基础价和允许浮动区间。
- 自动定价根据季节、客群需求、入住率、口碑和剩余房量在区间内调整。
- 每次建议或自动调整都显示原因。
- 玩家可锁定某房型价格或随时手动接管。
- 首版不做逐渠道、逐日历格和复杂促销的专业收益管理。

### 12.2 关键指标

经营中心默认显示：

- 入住率
- 平均房价
- 客房收益
- 公共空间收入
- 运营开销
- 净收益与利润率
- 可用现金、贷款与偿债
- 宾客口碑
- 各房型和客群表现

界面遵循“结果 → 原因 → 行动”：先展示关键结果，再解释变化原因，最后列出可处理事项。详细报表存在，但不阻塞日常游玩。

## 13. 员工与服务

- 按前厅、客房、餐饮、工程、安保、宾客关系等部门管理。
- 玩家任命部门负责人，设置预算、人数、培训和服务标准。
- 普通员工不逐个排班，只以汇总能力、成本和士气参与计算。
- 部门负责人提供明确专长，例如夜床服务、餐饮效率或宾客关系。
- 服务能力不足会造成等待、清扫延迟、口碑下降和收入损失。
- 首版不包含完整员工个人故事、技能树和班次系统。

### 14.1 空间类型

### 14.2 设计方式

公共空间共用客房设计器的网格、功能区、风格和 AI 流程，并增加专属工具：

- 餐厅：座位区、厨房、传菜、吧台和服务流线。
- 泳池：水体形状、池岸、湿区和救生动线。
- 水疗：接待、护理、湿区、安静度与私密性。
- 宴会：容量、舞台、后勤、灵活隔断和疏散。
- 大堂：入口、接待、等候、行李与电梯厅关系。

底层操作保持一致，内容目录、规划检查和经营指标按空间类型扩展。

### 14.3 经营深度

- 大堂、行政酒廊、泳池、健身房、花园等主要提供品牌、客群和满意度加成。
- 餐厅、酒吧、水疗和宴会空间拥有轻量经营：定位、价格、容量、开放时间、服务预算与特色项目。
- 餐厅可选择菜单结构和少量招牌菜，不管理逐项原料库存。
- 招牌菜影响餐厅口碑、客群吸引和非住店客流，并产生研发与食材成本。

## 16. 本地存档与安全

### 16.1 存档

- SQLite 保存经营、户型、房型、楼层、设计基因、任务和版本索引。
- AI 图片保存为独立资产文件，数据库只保存相对路径、哈希、MIME 类型和元数据。
- 每次施工、结算和采纳 AI 图片后建立恢复点。
- 保留最近 20 个自动备份，支持手动命名存档。
- 可导出完整 `.cloudinn` 存档包，包含数据库、图片、清单和版本信息。
- 导入时先验证清单、版本、哈希和可用空间，再创建新存档，不覆盖现有存档。

### 16.2 密钥与网络

- API Nebula 令牌保存在 macOS 钥匙串，不进入前端状态、普通配置、日志或存档包。
- 首版不要求注册账号，不上传完整经营存档。
- 仅在生成图片或启用可选 AI 点评时联网。
- 应用日志过滤鉴权头、Base64 图片和自由输入中的敏感内容。

### 16.3 写入可靠性

- 关键操作使用数据库事务。
- 图片先写临时文件并验证，再原子移动到资产目录，最后提交数据库引用。
- 事务失败时回滚；下次启动从最后完整状态恢复。
- 存档格式带版本号，升级前自动备份，迁移失败时保留旧存档。

## 17. 系统结构与模块边界

### 17.1 核心模块

- **应用外壳：** 窗口、菜单、本地文件、钥匙串、打包和系统通知。
- **房间设计：** 网格、功能区、门窗、物件、设计基因和造价评估。
- **楼层规划：** 房型实例、走廊、核心筒、后勤、复制和连通检查。
- **经营模拟：** 时间、客群、预订、定价、服务、财务、声望和离线结算。
- **公共空间：** 专属目录、规划检查与轻量经营配置。
- **AI 编排：** 标准任务、供应商适配、队列、重试、参考图、解析与版本。
- **存档与资产：** SQLite、图片文件、恢复点、迁移和导入导出。
- **内容目录：** 房型等级、家具、设施、风格、客群和建筑模板的数据配置。

模块通过明确的数据对象和命令通信。经营模拟不读取 AI 供应商响应；它只读取已经保存的房型属性与评分。AI 编排不能直接修改现金、入住率或评价分数。

### 17.2 结算数据流

1. 游戏时钟推进到结算点。
2. 经营引擎读取当前房态、客群需求、价格和服务能力。
3. 计算预订、入住、公共空间客流和服务结果。
4. 结算收入、成本、贷款、口碑和声望。
5. 在单个事务中写入结算与下一个状态。
6. 界面刷新数据和像素动线。
7. 若玩家启用 AI 点评，在事务完成后提交只读摘要。

同一存档状态、同一随机种子和同一输入应重现相同结算结果，便于测试和问题定位。

## 18. 异常处理

- **AI 超时或服务失败：** 任务保持可重试状态；可取消或切换备用模型；蓝图和经营不受影响。
- **模型不可用：** 运行前检查模型列表；主模型不可用时提示并切换备用模型，不静默降低已选择的高分辨率要求。
- **图片解析失败：** 不写入正式资产；保留任务错误摘要，不记录完整响应。
- **程序意外关闭：** 未完成事务回滚，下次启动从最后完整状态恢复。
- **图片文件缺失：** 存档仍可打开，显示占位图，并提供从备份恢复或重新生成。
- **存档迁移失败：** 保留原文件和升级前备份，不覆盖旧存档。
- **离线：** 已有内容和经营正常运行；新 AI 委托进入等待联网状态。
- **资金不足：** 阻止施工提交，但保留完整设计蓝图，并提供分期或贷款入口。

错误信息采用玩家可理解的语言，说明发生了什么、哪些内容安全、下一步可做什么。技术细节只放入可选诊断信息。

## 21. 分阶段交付原则

首个正式版本内容丰富，因此实施必须先经过较小内部原型：

1. **核心闭环原型：** 一种客房、一个小楼层、一个客群、基础结算、单张 AI 图和本地存档。
2. **设计与楼层垂直切片：** 完整网格、物件、房型变体、环形楼层、主视觉与区域图一致性。
3. **经营垂直切片：** 多客群、定价、部门、现金、贷款、日周月结算。
4. **内容扩充：** 公共空间、物件、风格、建筑楼层和百间客房规模。
5. **稳定与发布：** 性能、恢复、备份、导入导出、打包和长期存档验证。

每个阶段都交付可玩的闭环，不先堆积无法体验的底层系统。

## 22. 已确认决策摘要

- Mac 桌面应用采用 Tauri 混合技术，而非纯 Swift 或纯网页。
- 首版以完整的设计—布局—经营闭环为目标。
- AI 图首版是效果图，不是可直接移动家具的分层场景。
- 房间内部严格一致，酒店内部允许多个设计系列和特色房。
- 户型采用 0.5 米网格，拉框后用画笔修整。
- 关键高奢家具较丰富，并影响造价和轻度经营评分。
- 建筑采用模板与扩建；首个场景是摩天楼中的酒店。
- 楼层支持中央核心筒、环形走廊和真实面积房型。
- 经营采用自动定价、细分客群、部门级服务和轻量公共空间经营。
- 当前版本专注一家旗舰酒店，后续再扩展集团。
- 默认休闲，保留经营难度。
- 本地优先存档，API 密钥进入 macOS 钥匙串。
- 主生图模型为 API Nebula `gemini-3.1-flash-image`，备用为 `gemini-2.5-flash-image`。
